Create an AI agent that assembles agents from a catalog of composable parts, validates them, and evaluates them before they are deployed to a project.

First step is to define a taxonomy that supports composition of agents. Agents are composed, not inherited. See docs/Composable-Agent-Taxonomy.pdf for the full proposal and examples.

## Taxonomy

An **Agent** has a name, Traits, Skills, Hooks, LLMs, a preferred LLM (which must be in the LLMs list), a prompt, required Capabilities, and Evals. It may declare Outputs, named fields of its structured result, which only playbook handoffs read.

A **Trait** is a reusable fragment of behavior: a short prompt fragment plus optional tool grants or denials. Traits replace base agents. An agent lists its traits. The merge order is the map's pack base, then traits left to right, then skills, then the skills of mounted tools, then the agent's own prompt, then anything under `overrides`. Later text wins.

A **Skill** is a standalone module. It belongs to no agent. It declares what it requires (tools, minimum model tier), and any agent that satisfies the requirements can load it.

A **Tool** is an MCP server or toolchain. It declares the Capabilities it provides, its commands, and carries the Skill that teaches how to use it. A command whose exit status a playbook handoff relies on must say so in the tool file (kicad's `erc-gate` exits 5 on violations where `erc` exits 0).

A **Capability** is a named contract between agents and tools. Agents require capabilities. Tools provide them. No agent names a vendor.

**Evals** are mandatory on every agent and every playbook: a list of tasks with pass conditions. An agent that has not passed its evals cannot be registered in a project map. Adding a member to an agent re-runs its evals (issue-triager 3/3 after `outputs` was added).

A **Pack** is one external skill set (superpowers, gstack, GSD, pstack, super-board) pinned to a commit of its GitHub repo, whose base traits and skills apply to every agent in a project. The catalog holds one markdown file per pack with the link and the pin, never a copy; the validator fetches the pinned commit on first use. Decided 1 Nov 2026. A project map attaches at most one pack, so base skills never overlap or clash. The pack composes before the agent's own traits and skills, so the agent's text wins. An aspect may exclude part of the base with a reason. Decided 1 Nov 2026.

A **Playbook** is a sequence of agent invocations run by code, never read by a model. See Playbooks below.

## Conflicts

If two traits disagree on a tool, the agent must list the tool under `overrides.allow` with a reason. The validator rejects the file otherwise. A tool denied by any trait stays denied unless overridden.

## Project map

A project has an agent map made of named **Aspects**. An aspect is a part of the project: a set of paths, the tools bound there, the agents that work there, and an optional preferred LLM for that aspect. Tools bind to aspects, not to agents. A `shared_tools` list is visible in every aspect.

When an agent runs inside an aspect, its tool set is the aspect's tools plus shared tools, minus anything a trait denies. Tools bound to other aspects are not mounted.

Example: a UX design aspect binds Pen.dev, a mechanical aspect binds FreeCAD (freecad-mcp, routed to mechanical-engineer, capability `mechanical-cad`), an EDA aspect binds KiCAD (kicad-cli and kicad-sch-api, routed to drc-checker and schematic-engineer), a firmware aspect binds the STM32 toolchain. Swapping a tool is a one-line edit in the map.

## Validator rules

1. The preferred LLM is in the agent's LLMs list.
2. Every skill's requirements are satisfied by the agent.
3. The tools bound to an aspect provide every capability required by the agents routed there.
4. Trait conflicts carry an override with a reason.
5. A map names at most one pack, and its base is satisfiable by every agent routed in the map, or the aspect excludes it with a reason.
6. Every playbook beside a map names that map, every step's agent is routed in the step's aspect, every step but the last has one handoff that a bound tool command or a declared agent output can decide, every placeholder is a declared input, and the playbook has at least one eval with an `expect_path` that is a prefix of the step agents.

## Meta-agent loop

Given a request, the meta-agent selects traits, skills, and capabilities from the catalog, emits an agent file with evals, runs the validator, runs the evals, and reports pass or fail before anything is registered in the project map. When a map and aspect are given, the proposal sees the map's pack base so it does not repeat it, the validator checks rule 5 with the new agent routed in, and the evals run with the pack composed first.

## Notation

Agent, trait, skill, tool, pack, playbook, and map files are YAML with markdown bodies. Decided 1 Nov 2026, after rule 6 and `run_playbook.py` existed: no symbolic notation.

The playbook was the strongest case for one, since no model reads it, so model fluency in YAML does not protect it. Measured on the two playbooks: a one-line form such as `schematic-engineer@eda-design -[kicad.erc-gate file={file}]-> drc-checker@eda-design` replaces 6 of the 23 non-comment lines (the `steps` key, two agents, two aspects, one handoff). The other 17 (name, description, map, inputs, one task per step, and evals with inputs, `expect_path`, `pass_if`) shorten under no notation, and the tasks would still need keying to steps, which a one-line path cannot do once an agent appears twice. On the consumer side, four programs read these files (`validate.py`, `run_evals.py`, `run_playbook.py`, `make_agent.py`) and none has a parser of its own; rule 6 is 118 lines and every line is a semantic check (routed, bound, declared, prefix). A notation would add a parser to each program, a grammar, and a second language in error messages, and remove nothing. `make_agent.py` emits agents as JSON against a schema and prints YAML; a notation would need a model writing a language it has never seen, or a second printer.

What the files do contain is three conventions inside YAML scalars, each added the day a consumer needed it and each parsed by one line: `{name}` placeholders in tasks and commands, `tool.command` references in handoffs, and `expect_path` as an ordered list of agents that must be a prefix of the steps. With the rule that list order is merge order, that is the notation. `registry-sources.yaml` (2 Nov 2026) adds no convention: `{name}` in its `layout` is the pack placeholder, and `provides` is the tool key it already was. It reopens on one trigger: an eval that needs a branching playbook, because a linear playbook is a list and a branching one is a graph, and a graph in YAML is where a notation would first pay for its parser.

## Playbooks

Decided 1 Nov 2026: a playbook is a multi-step procedure, not a routing table. The map already is the routing table (aspects route agents by path); a trigger, when one is needed, is one line at the head of a playbook, not a new kind of file.

A playbook is an ordered list of steps. Each step names a catalog agent, the aspect of a map it runs in, and a task. Between steps is a handoff condition that code evaluates. What distinguishes a playbook from a skill is who reads it: a skill is read by a model inside one agent's context; a playbook is read by the runner, and no agent ever sees it. If a model would have to read it to follow it, it is a skill.

Handoff conditions are decided by code, never by a model. Two forms: `command`, one of the aspect's tool commands, passing on exit status zero; and `output`, a comparison on a field of the previous agent's structured result, which requires that agent to declare an `outputs` schema and end its final message with a matching JSON block. The runner prefixes each step's task with the diff the previous step made, since a later agent has no other way to know what changed. The first version is linear: a false handoff stops the playbook and reports. No branching, retries, or loops until an eval needs them, and a handoff tests one field or one command.

Playbooks live in `projects/<name>/playbooks/`, beside the map, because a step needs an aspect and aspects exist only in a map. Evals are mandatory, as for agents, and each states the `expect_path` through the steps as well as the final `pass_if`, so a wrong handoff fails even when the last agent succeeds.

Rule 6 (in the validator since 1 Nov 2026): every step's agent is routed in the named aspect, every `output` condition names a field the previous agent declares, every `command` condition is provided by the aspect's tools plus `shared_tools`, and a playbook has at least one eval. `catalog/run_playbook.py` runs a playbook's evals, or one run with given inputs.

Playbooks so far: `projects/smart-thermostat/playbooks/schematic-change-and-check.yaml` (schematic-engineer, then drc-checker if ERC passes; command handoff) and `triage-and-review.yaml` (issue-triager, then security-reviewer if severity is high or critical; output handoff on the triager's `outputs`).
