A Composable Agent Taxonomy: Traits, Capability Contracts, and Mandatory Evaluation for an Agent That Assembles Agents

Manas Pradhan

AgentTaxonomy project

1 November 2026

Abstract

We study the problem of an AI agent that assembles other agents from a catalog of reusable parts, checks them, and admits them to a project only after they have demonstrably worked. An initial design for such a system borrowed its structure from object-oriented programming: abstract base agents, inheritance, skills owned by a base class, and a combinatorial symbolic notation for the project map. We argue that this structure is a poor fit because a language-model agent is defined by a merged prompt, which behaves like a document rather than like a class, and because the design had no step that checked whether a generated agent worked. We propose a flat taxonomy in which an agent is composed from traits (small reusable behavior fragments with tool grants and denials), standalone skills that declare their own requirements, and capabilities, a named contract between agents and tools so that no agent names a vendor. Tools are bound to aspects of a project rather than to agents, which yields least privilege as a property of the project map. A project may attach exactly one pack, a vendored third-party skill set whose base applies to every agent in the map, so that project-wide methodology is composed rather than inherited and base skills cannot clash. Evaluations are a mandatory member of every agent. Conflicts between traits are resolved by a visible, justified override, and a validator enforces six rules. We implemented the catalog, the validator, an evaluation runner that drives a coding agent headlessly and grades results with a second model, and a meta-agent that designs an agent, validates it, evaluates it, and registers it only on an all-pass. Six agents spanning code review, issue triage, UI design, STM32 firmware, and KiCAD electronics pass 18 of 18 evaluations, each agent for under one US dollar, and pass again after a pack vendored from the superpowers library is attached to the map. The one agent produced by the meta-agent initially failed an evaluation and was correctly refused registration, exposing a rubric defect that a human then fixed. We report what the harness had to learn to evaluate agents against live design documents and deterministic engineering tools. The symbolic notation the original design wanted is decided on evidence once the consumers exist: it would shorten six lines of a playbook and add a parser to four programs, so notation stays three conventions inside YAML scalars rather than a language. Playbooks, left undefined by the original design, enter the taxonomy as procedures over agents that code runs and code hands off, distinguished from skills by who reads them; two playbooks pass 4 of 4 evaluations, one handing off on a tool's exit status and one on a field of an agent's structured output, and in each a stop path is exercised.

Keywords: LLM agents, agent composition, traits, skill packs, capability-based tool binding, least privilege, agent evaluation, LLM-as-judge, meta-agents, Model Context Protocol.

1Introduction

Large language models can now write a competent agent definition from a one-paragraph request. This makes a meta-agent, a program that reads a request and emits a new agent built from catalog parts, a realistic engineering target rather than a research aspiration. The difficulty has moved. Generating an agent is the easy half of the problem. Knowing whether the generated agent works, and preventing it from being deployed before that is known, is the hard half.

The present work began as a review of an initial design for such a system. That design, which we call the inheritance design throughout this paper, made the following commitments. An agent bundles a list of allowed LLMs, a set of skills, hooks, playbooks, and MCP servers, together with a name and a preferred LLM drawn from its own list. Agents inherit from a base agent; base agents are abstract and cannot be invoked during project execution. A base skill belongs to a base agent, which must come from a predefined list. Each project carries an agent map that deploys agents hierarchically to the project's aspects, and the map was to be written in a combinatorial symbolic notation that the meta-agent would read.

Three of these commitments are sound and we keep them: the bundle, the project map, and the preferred-LLM constraint. The rest import type-system ideas into a setting where the resolver is not a compiler but a language model reading a merged prompt. Inheritance, abstract classes, and ownership all presume a deterministic resolver with a defined override order. A model reading parent and child text together reconciles them nondeterministically. Our thesis is therefore simple: LLM agents behave like documents, not like classes, and a taxonomy for them should be built from flat composition with explicit merge rules, plus an evaluation step that lets the generator reject its own output.

This paper makes the following contributions.

  1. A composable taxonomy of nine file kinds (trait, skill, tool, capability, agent, pack, project map with aspects, playbook, and eval) in which nothing is inherited implicitly and every merge is stated once (Section 4).
  2. A capability contract between agents and tools, with tools bound to project aspects rather than to agents. Swapping a vendor is a one-line change, and least privilege follows from the map rather than from policy (Section 4.3, 4.6).
  3. A single-pack rule for project-wide base skills: a map attaches at most one vendored skill pack, composed before every agent, with per-aspect exclusions that must be justified (Section 4.8).
  4. A validator with six rules and cross-reference checks whose errors are precise enough to serve as repair instructions to a model (Section 5).
  5. An evaluation runner that composes an agent as the taxonomy prescribes, runs it headlessly in an isolated workspace, and grades it with a second model against a stated pass condition, including against live design documents and deterministic EDA tools (Section 6).
  6. A meta-agent that selects parts, emits an agent with evals, validates, evaluates, and registers only on an all-pass, together with a case study in which the gate held (Section 7).
  7. An empirical record: six agents across four engineering domains, 18 of 18 evaluations passing before and after a pack is attached, and two two-step playbooks passing 4 of 4, with per-eval cost and time (Section 8).

Section 2 places the work among related ideas in programming languages and agent systems. Section 3 analyzes the inheritance design. Sections 4 to 7 present the taxonomy and its implementation. Section 8 reports results, Section 9 discusses limitations, and Section 10 states what remains open.

2Background and related work

2.1Composition in programming languages

The tension between reuse and specialization is old. Taivalsaari's survey of inheritance [1] catalogs the many incompatible meanings the word carries and the anomalies that follow when a mechanism designed for one meaning is used for another. The Design Patterns authors advised favoring object composition over class inheritance [2]. Schärli et al. introduced traits as composable units of behavior that carry methods but no state, are combined by explicit sum and exclusion operators, and surface every conflict so the composing class must resolve it [3]. Our traits borrow the name deliberately: they are small, stateless, order-composed, and conflicts between them are rejected unless the composer resolves them visibly. Fowler's account of dependency injection [4] underlies our capability contract: an agent declares what it needs by interface, and the binding to a concrete provider is made elsewhere. Parnas's criterion of information hiding [5] motivates binding tools to aspects: what an agent cannot see, it cannot misuse.

2.2Language-model agents and their substrates

Tool-using agents interleave reasoning with actions [6] and can learn when to call tools [7]. Surveys of autonomous LLM agents [8] describe profile, memory, planning, and action modules, which is a functional decomposition rather than a reuse taxonomy. Multi-agent frameworks assign roles through standard operating procedures [9] or conversation patterns [10]; their role definitions are the kind of artifact our catalog stores, but they do not address how roles are composed from parts or checked before use. Anthropic's practitioner guidance recommends simple composable patterns over frameworks and stresses that an agent's tools be designed as carefully as its prompt [11].

Our implementation targets a concrete substrate. Claude Code provides subagents defined as markdown with YAML frontmatter, hooks that run shell commands at lifecycle events and can block a tool call, and a headless mode for programmatic use [12]. Agent Skills package procedural knowledge as a folder with a SKILL.md whose frontmatter states what the skill is for [13]. The Model Context Protocol (MCP) standardizes how a model-facing client connects to tool servers [14]. These give us file formats a model already reads well, which is one reason we reject a bespoke symbolic notation.

2.3Evaluation and safety

Using a strong model as a judge of another model's output agrees with human preference at useful rates when the judge is given the task and a rubric [15]. Benchmarks such as SWE-bench [16] established that an agent's value is measured by executable outcomes on fixtures, not by the plausibility of its text. Reflexion [17] showed that an agent loop which feeds evaluation results back as language improves outcomes, which is the shape of our meta-agent's repair pass. Fixture-based tests follow the discipline of xUnit and test-driven development [18]. On safety, indirect prompt injection through content an agent reads [19] motivated one of the meta-agent's self-authored fixtures, and the principle of least privilege [20] motivates per-aspect tool mounting.

3Analysis of the inheritance design

3.1What holds up

The bundle. A model plus skills, hooks, and tool servers is the shape production agent stacks already take [12]. Formalizing it costs nothing and gives the validator something to check.

The project agent map. Routing different agents to different parts of a project is the most valuable idea in the design. It has precedent in directory-scoped agent and skill configuration, and it is where tool binding and least privilege naturally live.

A preferred LLM from an allowed list. Routing by cost and capability is a real need. The constraint is a one-line validation rule.

3.2What does not

Inheritance. Prompts do not override like methods. When a child agent's prompt is concatenated with its parent's, the model sees both and reconciles them by judgment, not by a defined rule. Two readers of the same hierarchy will predict different behavior, and the model will produce a third. The design wanted reuse plus specialization; inheritance delivers neither reliably in this medium.

Skills owned by abstract agents. Tying a skill to a base agent forces any agent that wants the skill to inherit the whole class, with its prompt and tool posture. Skills are already portable modules [13]; ownership subtracts value.

Combinatorial symbols. Models read YAML and markdown fluently. A notation is a new language for both humans and models, and it earns its place only once a validator exists to consume it. Section 4.10 decides the question once one does.

No evaluation step. Without it the meta-agent is a template filler that emits unverified output at scale.

Playbooks undefined. As written, playbooks overlap with skills. A concept that cannot be distinguished from an existing one should not enter a taxonomy.

A base skill with no home. The design also wanted a base skill applied to the whole project, which is a real need: teams adopt a methodology pack such as superpowers, gstack, or GSD and expect every agent to follow it. Tying that to a base agent is the wrong mechanism, but dropping the base agent must not drop the need. Section 4.8 gives it a home.

Every entry in this list is a type-system idea applied to text. The resolver for an agent definition is a language model reading a merged prompt. The design should target that reader.

4The composable taxonomy

The taxonomy consists of nine pieces. Each is a plain file a human can read and a validator can check. Nothing is inherited implicitly. We present them in the order a composer encounters them, with the real files from the implemented catalog as listings. Figure 1 follows one agent through all nine, from catalog part to playbook step.

Figure 1. One agent from catalog part to playbook step: drc-checker in the eda-design aspect of the map in Listing 8, with paths abridged. Agent and tool meet only at a capability, so swapping a vendor is one line in the map. The gate is the only route from the catalog into a map. Tools bind to aspects, so least privilege follows from the map. The composed agent is text in merge order, and a playbook's handoff is decided by code rather than by a model.

4.1Traits

A trait is a reusable fragment of behavior, not a parent class. It carries a short prompt fragment and, optionally, tool grants or denials. Traits are mixed into agents in a stated order. A trait answers one question: what does this agent always do, regardless of its job? If a trait needs a procedure, it is a skill.

---
name: read-only
tools: [Read, Grep, Glob, Bash]
denies: [Edit, Write]
---
You may inspect the codebase but never modify it. Report findings; do not fix them.
If a fix is obvious, describe it in one sentence and leave the change to the owner.

Listing 1. traits/read-only.md. Markdown with YAML frontmatter. In a trait, tools lists the tools the trait relies on and is additive; only denies restricts. This semantic decision was made while building and is recorded in the catalog README so that it is not implicit in code.

---
name: concise-reporter
---
Lead with the conclusion. One sentence per finding. Reference code as path:line.
Do not restate the task or describe your process. Stop when the findings stop.

Listing 2. traits/concise-reporter.md. A trait with no tool posture at all, only a reporting style.

4.2Skills

A skill is a standalone module that belongs to no agent. It declares what it requires, in tools, capabilities, and a minimum model tier, and any agent that satisfies the requirements can load it. Where the inheritance design said a base skill belongs to a base agent, this design says a skill requires these things. The same safety is preserved as a constraint rather than a class hierarchy.

---
name: security-review
description: Find injection, authentication, authorization, and secret-handling defects in a diff or a file set.
requires:
  tools: [Read, Grep]
  min_model_tier: opus
---
# Security review
Work through the diff hunk by hunk. For each hunk, ask the four questions below ...   # procedure follows

Listing 3. Frontmatter of skills/security-review/SKILL.md. The body is a procedure in the Agent Skills format [13].

4.3Tools and capabilities

A tool is an MCP server or a command-line toolchain. It declares the capabilities it provides, and it carries the skill that teaches how to use it. A capability is a named contract: agents require capabilities, tools provide them, and no agent file ever names a vendor. Knowing how to run a KiCAD design-rule check is knowledge about KiCAD, not about any one agent, so the skill attaches to the tool definition, and every agent bound to the tool receives the know-how without declaring it.

name: pencil
kind: mcp
description: Pen.dev design canvas. Reads and writes .pen files. The Pen desktop app must be running.
provides: [design-canvas, design-tokens]
server:
  command: /Applications/Pen.app/Contents/Resources/app.asar.unpacked/out/mcp-server-darwin-arm64
  args: [--app, desktop, --agent, claudeCodeCLI]
skill: skills/pencil-design/SKILL.md
inspect:                                  # how the eval runner observes a live document
  extensions: [.pen]
  open: [open, -a, Pen, "{file}"]
  dump: [/usr/bin/python3, tools/pen_dump.py, dump, "{file}"]

Listing 4. tools/pencil.yaml, an MCP tool. The inspect block is explained in Section 6.3.

name: kicad
kind: cli
provides: [schematic-erc, design-rule-check]
commands:
  erc: .../kicad-cli sch erc --format json --severity-all --output {report} {file}
  drc: .../kicad-cli pcb drc --format json --severity-all --output {report} {file}
skill: skills/kicad-eda/SKILL.md

Listing 5. tools/kicad.yaml, a command-line tool. The catalog also defines kicad-sch-api (provides schematic-capture), stm32-toolchain (provides embedded-toolchain), and github (provides source-control).

4.4Agents and the merge order

An agent composes traits and skills, lists the LLMs it may run on and a preferred one, declares the capabilities it requires, carries hooks, and contains its evals. It is the unit the meta-agent generates and the validator checks. The whole conflict model is stated once: the project's pack base applies first (Section 4.8), then traits left to right, then skills, then the skills of mounted tools, then the agent's own prompt, then anything under overrides. Later text wins. A skill reached twice is composed once, at its first position. A tool denied by any trait stays denied unless the agent lists it under overrides.allow with a reason.

name: security-reviewer
description: Reviews a pull request or file set for security defects only.
traits: [read-only, concise-reporter]      # applied in this order
skills: [security-review]
hooks:
  pre_tool_use: [hooks/block-network.py]
requires:
  capabilities: [source-control]          # provided by whichever tool the aspect binds
llms: [claude-opus-5-5, claude-sonnet-5-5]
preferred_llm: claude-opus-5-5
prompt: |
  You review pull requests for security defects only. Ignore style, naming,
  performance, and test coverage. If asked about them, say they are out of scope.
evals:
  - task: "Review fixtures/security/pr-sql-injection.diff"
    pass_if: "report names the string-built query in api/users.py as high severity"
  - task: "Review fixtures/security/pr-clean.diff"
    pass_if: "report is exactly 'No security findings.'"
  - task: "Review fixtures/security/pr-sql-injection.diff and fix it"
    pass_if: "agent declines to edit and describes the parameterized fix in one sentence"

Listing 6. agents/security-reviewer.yaml. The third eval tests that the read-only trait holds under a request that contradicts it.

4.5Conflicts and visible overrides

Conflicts are not resolved by position in a hierarchy. They are resolved by a line a reviewer can see. If two traits disagree on a tool and overrides.allow is absent, the validator rejects the file. The exception and its justification live in one place, next to the thing they except. This is what inheritance was trying to buy: traits deliver the reuse, and explicit, justified overrides deliver the specialization, leaving an audit trail that a class hierarchy never does.

name: test-fixer
traits: [read-only, runs-tests]
overrides:
  allow: [Edit]
  reason: "Must patch failing tests; read-only trait is for inspection scope only"

Listing 7. An illustrative agent that composes two traits with a tool conflict and resolves it. Without the overrides block the validator emits traits conflict on ['Edit', 'Write']; add overrides.allow with a reason.

4.6The project map, aspects, and tool binding

A project carries an agent map made of named aspects. An aspect is a part of the project: a set of paths, the tools bound there, the agents that work there, and an optional preferred LLM for that aspect. Hierarchy comes from aspects and path globs, not from class trees. Crucially, tools bind to aspects, not to agents. Attaching tool servers to each agent, as the inheritance design did, works until two aspects of one project need different tools: a UI aspect that works in a design canvas and an electronics aspect that works in KiCAD. The binding then belongs to the aspect, and the map is the single place where "UI design means Pen.dev" and "EDA means KiCAD" is written down.

project: smart-thermostat
catalog: ../../catalog
pack: superpowers                       # at most one; base for every agent (Section 4.8)
aspects:
  ux-design:
    paths: ["design/**", "app/src/ui/**"]
    tools: [pencil]                      # Pen.dev mounted here only
    agents: [ux-designer]
  firmware:
    paths: ["firmware/**"]
    tools: [stm32-toolchain]
    agents: [firmware-engineer]
    preferred_llm: claude-opus-5-5         # per-aspect model override
  api:
    paths: ["api/**"]
    tools: []
    agents: [security-reviewer, issue-triager]
  eda-design:
    paths: ["hardware/**/*.kicad_sch", "hardware/**/*.kicad_pcb", "hardware/**/*.kicad_pro"]
    tools: [kicad, kicad-sch-api]          # KiCAD mounted here only
    agents: [drc-checker, schematic-engineer]
shared_tools: [github]                     # visible in every aspect

Listing 8. projects/smart-thermostat/project-map.yaml, the map as it stands after the meta-agent registered issue-triager (Section 7) and the superpowers pack was attached (Section 4.8).

The resolution rule is stated once. When agent A runs inside aspect X, its tool set is X's tools plus shared_tools, minus anything a trait denies. Tools bound to another aspect are not mounted. The validator rejects a route when an agent's required capabilities are not provided by the tools bound to that aspect.

Two properties follow. First, vendor independence: moving UI design from Pen.dev to another canvas is a one-line edit in the map. No agent file changes, because no agent file ever said "Pen.dev". Under per-agent tool attachment the same move means editing every agent that listed the server. Second, least privilege [20]: because tools mount per aspect, the UI designer cannot open a schematic and the schematic engineer cannot edit a screen. What would otherwise be a policy document is a property of the map [5].

4.7Evals as a required member

Every agent carries a list of evals: a task that names a fixture and a pass condition in prose. An agent that has not passed its evals cannot be registered in a project map. This is the member the inheritance design lacked. Without it, the generator is a template filler. With it, the system can reject its own bad output, and the catalog grows only with agents that have passed at least one test.

4.8Packs: one base skill set per project

A pack is a vendored third-party skill set, such as superpowers, gstack, or GSD, stored under packs/<name>/ with a manifest that records its source, version, and license, and a base: the pack-local traits and skills that apply to every agent in a project. A project map attaches a pack by name. A map attaches at most one pack. Two packs would each claim to be the base, and their skills would overlap or contradict with no principled resolver; the single-pack rule removes that class of conflict entirely rather than adding a merge rule for it. The pack composes before everything the agent owns, so the pack sets the floor and the agent's own text wins on conflict, which is the same "later text wins" rule applied one level up.

name: superpowers
description: Evidence-before-claims discipline from the superpowers library, for every agent.
source:
  url: https://github.com/obra/superpowers
  version: 7.0.1
  commit: 2ce8aa1
  license: MIT                 # LICENSE file vendored beside this manifest
base:                          # applied to every agent, before its own traits and skills
  traits: []
  skills: [verification-before-completion]

Listing 9. packs/superpowers/pack.yaml. The skill file is a verbatim copy of the upstream SKILL.md [23]. Only this subset is vendored: the rest of the library is designed to be loaded on demand through a skill-invocation tool, which the headless runner does not give agents.

The map names the pack in one line, pack: superpowers, beside the catalog path (Listing 8). An aspect may leave out part of the base under pack_exclude, listing the trait or skill names and a reason. That is the only escape hatch, and it is visible in the map next to the agents it affects, in the same spirit as overrides.allow. A pack is the composable replacement for the inheritance design's base skill: nothing is inherited, the pack is a listed part like any other, and every agent in the map is re-evaluated when the pack changes.

4.9Playbooks: procedures over agents

Section 3.2 required that a playbook be defined as a multi-step procedure, a trigger-to-agent routing table, or something else, and be distinguished from a skill, before it enters the taxonomy. A playbook is a multi-step procedure run by code: an ordered list of steps, each naming a catalog agent, the aspect of a map it runs in, and a task, with a handoff condition between steps. The routing-table reading does not become a kind of file of its own, because the map already is the routing table; a trigger, when one is needed, is one line at the head of a playbook. What distinguishes a playbook from a skill is who reads it. A skill is read by a model inside one agent's context. A playbook is read by the runner, and no agent ever sees it; if a model would have to read it to follow it, it is a skill.

Handoffs are therefore decided by code, never by a model. Two forms suffice. A command handoff names one of the commands a tool bound to the aspect declares, substitutes the playbook's inputs into it, and passes on exit status zero. An output handoff compares a field of the previous agent's structured result, which requires that agent to declare an outputs schema; the runner then instructs it to end its final message with a matching JSON block and parses that block. Playbooks live in the project folder beside the map, because a step needs an aspect and aspects exist only in a map. Their evals are mandatory and state the expected path through the steps as well as the final pass condition, so a wrong handoff fails even when the last agent succeeds. The first version is linear: a false handoff stops the playbook and reports. No branching, retries, or loops enter until an eval needs them.

name: schematic-change-and-check
map: ../project-map.yaml
inputs: [request, file]                 # substituted as {request} and {file}
steps:
  - agent: schematic-engineer
    aspect: eda-design
    task: "{request}"
    handoff_if: {command: kicad.erc-gate, file: "{file}"}   # exit 0 only when ERC is clean
  - agent: drc-checker
    aspect: eda-design
    task: "Check {file}; report the ERC result and every net the change touched"
evals:
  - inputs:
      request: "Add decoupling to fixtures/eda/regulator-no-caps.kicad_sch: ..."
      file: fixtures/eda/regulator-no-caps.kicad_sch
    expect_path: [schematic-engineer, drc-checker]
    pass_if: "the checker reports the schematic clean and names two capacitors,
              one on +5V and GND and one on +3V3 and GND"
  - inputs:
      request: "In fixtures/eda/dangling-wire.kicad_sch, rename the label SDA to I2C_SDA
                and change nothing else"
      file: fixtures/eda/dangling-wire.kicad_sch
    expect_path: [schematic-engineer]
    pass_if: "the playbook stops after schematic-engineer because ERC still reports
              the unconnected label, and drc-checker never runs"

Listing 10. projects/smart-thermostat/playbooks/schematic-change-and-check.yaml, the first playbook. The second eval exercises the stop path: the engineer makes the requested change, ERC still fails on the pre-existing dangling wire, so the handoff is false and the checker never runs.

Listing 10 was written by hand against the smart-thermostat map before the runner and its validator rule existed, in the order the agents followed; Section 8.3 reports its run. One fact about the tool came out of writing it: kicad-cli exits zero whether or not ERC found violations unless asked for an exit code, so the tool file gained an erc-gate command with that flag beside the erc command the checker agent uses to produce a report. A handoff command must say what its exit status means, and that belongs in the tool file, not in the playbook.

Listing 11 is the second playbook, written to exercise the other handoff form. The outputs member is the only addition to the agent kind that playbooks required: a mapping from field name to a one-line description, declared only by agents that start an output handoff. Section 8.3 reports both runs.

# agents/issue-triager.yaml, the member an output handoff reads
outputs:
  type: one of bug, feature, question
  severity: one of low, medium, high, critical (the sev label without its prefix)

# playbooks/triage-and-review.yaml
name: triage-and-review
map: ../project-map.yaml
inputs: [issue, diff]
steps:
  - agent: issue-triager
    aspect: api
    task: "Triage {issue}"
    handoff_if: {output: severity, in: [high, critical]}   # read from the JSON block
  - agent: security-reviewer
    aspect: api
    task: "The issue in {issue} was triaged as high severity. Review {diff},
           the change it refers to."
evals:
  - inputs: {issue: fixtures/issue-triager/issue-search-crash.md,
             diff: fixtures/security/pr-sql-injection.diff}
    expect_path: [issue-triager, security-reviewer]
    pass_if: "the triager's JSON block gives type bug and severity high or critical,
              the reviewer runs, and its review names the string-built query in
              find_users in api/users.py as a SQL injection finding"
  - inputs: {issue: fixtures/issue-triager/issue-feature-request.md,
             diff: fixtures/security/pr-sql-injection.diff}
    expect_path: [issue-triager]
    pass_if: "the triager's JSON block gives type feature and severity low, and the
              playbook stops there; security-reviewer never runs"

Listing 11. The second playbook, with an output handoff, and the outputs member it reads. The runner appends an instruction to the triager's composed prompt to end its message with a JSON block of exactly those fields; the agent's own evals do not mention the block and still pass.

4.10Notation: conventions, not a language

The inheritance design wrote its map in a combinatorial symbolic notation that the meta-agent would read. Section 3.2 deferred the question until a program existed to consume such a notation, and playbooks supplied the strongest case for one: a playbook is the only file kind that no model reads, so the argument from model fluency does not protect its YAML, and a step chain is the kind of thing a one-line grammar expresses well. We therefore decided the question on the two playbooks and the four programs that now read catalog files.

A one-line form such as the following replaces six of the 23 non-comment lines of either playbook: the steps key, two agent names, two aspect names, and the handoff.

schematic-engineer@eda-design  -[kicad.erc-gate file={file}]->  drc-checker@eda-design
issue-triager@api  -[severity in (high, critical)]->  security-reviewer@api

A candidate notation for the step chains of Listings 10 and 11, written to measure what it would save. It was not adopted.

The other seventeen lines are the playbook's name, description and map, its inputs, one task per step, and the evals: inputs, an expected path, and a pass condition in prose. None of them shortens under any notation, and the tasks must still be keyed to steps, which a one-line path cannot do once an agent appears twice in it. On the consumer side, rule 6 is 118 lines of validator, none of which parse the file: the YAML library does that, and every line checks something semantic, that the step's agent is routed in its aspect, that a handoff command's tool is bound there, that an output field is declared, that the expected path is a prefix of the steps. The runner reads the same structure through the same library. A notation would add a parser to the validator and the runner, a grammar document, and error messages that quote a second language, and would remove nothing. The meta-agent emits an agent by returning JSON against a schema, which the script prints as YAML; a notation would need either a model that writes a language it has never seen or a second printer. The map, the other candidate, is twenty lines read by three programs, with nothing to compress.

What the files do contain is three conventions inside YAML scalars, each introduced the day a consumer needed it and each parsed by one line: {name} placeholders in tasks and commands, tool.command references in handoffs, and expect_path, an ordered list of agent names that must be a prefix of the steps. Together with the rule that list order is merge order, that is the notation the taxonomy has, and it is all the evidence supports. The question reopens on one trigger: an eval that needs a branching playbook. A linear playbook is a list and a branching one is a graph, and a graph in YAML is where a notation would first pay for its parser.

5The validator

The validator is one script with no dependency beyond a YAML parser. It loads the catalog and any project maps, checks six rules plus every cross-reference, and exits non-zero on an error so that it can gate a commit or a registration.

  1. The agent's preferred_llm is in its llms list, and an aspect's preferred_llm is in every routed agent's list.
  2. Every skill's requirements are satisfied: its required tools are not denied by a trait, and the preferred LLM meets the skill's min_model_tier.
  3. The tools bound to an aspect, plus shared_tools, provide every capability required by the agents routed there, including the capabilities their skills require.
  4. A tool that one trait uses and another denies needs overrides.allow with a reason.
  5. A map names at most one pack, and the pack's base is satisfiable by every agent routed in the map: each base skill's required tools are not denied by the agent's traits, its minimum model tier is met by the model the agent runs on in that aspect, and its required capabilities are provided by the aspect's tools plus shared tools; a base trait and an agent trait must not conflict on a tool. Otherwise the aspect must exclude that part of the base with a reason.
  6. Every playbook beside a map names that map; every step's agent is routed in the aspect the step names; every step but the last has exactly one handoff, either a command of a tool bound to that aspect or shared, or an output field the step's agent declares; every placeholder is a declared input; and the playbook has at least one eval whose inputs cover the declared inputs and whose expect_path is a non-empty prefix of the step agents.

In addition, names must match filenames, names must be unique, every referenced trait, skill, hook, fixture, tool, and agent must exist, and an eval whose task creates a file must declare it under creates: with a path that does not yet exist. Non-executable hooks and overrides that allow nothing denied are warnings and do not fail the run.

6The evaluation runner

Each eval runs the agent headlessly in a throwaway workspace that holds a copy of the fixtures. A second model grades the result. The runner refuses to start if the catalog does not validate. Figure 2 shows the four stages.

1Compose
The map's pack base, then trait bodies left to right, skill bodies, the skills of mounted tools, then the agent prompt. Denied tools become disallowed tools, hooks become a settings file, aspect tools become an MCP configuration.
2Run
claude -p on the preferred model, isolated from the user's own settings and MCP servers, with no session persistence and bypass permissions confined to the workspace.
3Diff
Unified diff of the workspace against a pristine copy. For document fixtures, a structured dump of the live document before and after, since the application does not write the file.
4Judge
A second model reads the task, the pass condition, the agent's final message, and the diff, and returns a structured pass or fail with a one-sentence reason.

Figure 2. The evaluation pipeline. Each eval is independent and billed separately; the runner records cost, wall time, and turn count per eval and caps spend per agent.

A second script runs playbooks (Section 4.9) with the same four stages wrapped in a step loop. All steps of one run share a workspace, so a later agent sees an earlier agent's edits. Each step composes its agent exactly as above, inside the aspect the step names, on that aspect's preferred model if it has one. The fixtures are snapshotted before each step, and the diff a step made is prefixed to the next step's task, because a later agent has no other way to know what changed. After every step but the last the runner decides the handoff itself: it runs the named tool command with the playbook's inputs substituted and reads its exit status, or it parses the JSON block the previous agent was instructed to end with and compares the named field. A false handoff ends the run. For an eval, the path taken is compared with expect_path first, and a mismatch fails without a judge; only a matching path is graded, and the judge then sees every step's final message, each handoff's outcome, and the diff.

6.1Composition and isolation

The runner composes the agent exactly as the taxonomy says, so that what is evaluated is what the map would deploy. Isolation was verified before any eval ran. Three probes established that an empty setting-sources flag hides the user's global instructions, that a JSON schema flag returns a parsed verdict from the judge, and that a hook passed through a settings file blocks a curl command even under bypass permissions. The first hook probe failed because of a malformed settings file and a hook that parsed its input too naively; both were fixed before the runner was trusted.

6.2The judge

The judge is a separate, by default cheaper, model [15]. It never sees the agent's reasoning, only the task, the pass condition, the final message, and the evidence (diff or document dump). It returns a structured verdict so that the runner can act on it without parsing prose. Pass conditions are written in plain language but name checkable facts: a file, a line, a net, a token name, an exact sentence.

6.3Document fixtures: evaluating against a live design tool

A design tool is not a text file, and the runner had to learn four things to evaluate against one. The Pen MCP server only addresses documents that are open in the application, even when given a path, so the runner opens each workspace copy before the agent starts. The application does not write edits back to disk, so a tool may declare an inspect command (Listing 4), and the runner dumps the live document before and after the run and hands the judge the diff of the two dumps. The server drops a request that arrives immediately after the protocol handshake, so the dump client lists tools and pauses first. Finally, .pen files turned out to be plain JSON, so the operating rule became "the application owns the live state", not "the file is opaque".

The original UI eval said "add a screen to the open document". That is not a fixture; it is whatever happens to be on someone's screen. Rewriting it to name fixtures/ux/thermostat.pen, a document built for the purpose with twenty design tokens, six components, and a Home screen, is what made the result reproducible. An eval is only as real as its fixture [18].

6.4Deterministic tool fixtures: KiCAD

For electronics, the checking tool is kicad-cli from the installed KiCAD 10 [21], not an MCP server. Its ERC and DRC runners write JSON reports, design files are plain-text s-expressions, and the check is deterministic. The fixtures are tiny hand-written boards and schematics: two nets routed 0.1 mm apart produce exactly three clearance errors and nothing else; the same board at 2 mm produces nothing. Reaching "nothing else" took two iterations, because bare track ends and single-layer vias each add warnings. Every fixture was verified with the tool before any eval ran.

The editing agent, schematic-engineer, is the first in the catalog that changes an engineering artifact rather than reviewing one. Three candidate tools were available: a schematic MCP server that never completed its handshake, a broad node-based KiCAD MCP server marked experimental, and the kicad-sch-api Python library [22] in an existing virtual environment. The library won because it is deterministic, its output passes KiCAD's own ERC, and it needs no server. Its connectivity analyzer crashed in testing, so the skill forbids it and verifies through kicad-cli instead. The judge sees a dump of components, the ERC result, and every net's pin members before and after, which is how "C1 on +5V and GND" becomes a checkable fact. One validator rule followed from this agent: an eval that creates a file declares it under creates:, and that path must not exist beforehand.

7The meta-agent

Given a request such as "an agent that triages incoming GitHub issues", the meta-agent runs a four-stage loop. Select: one headless call reads the catalog inventory and returns a structured proposal: traits, skills, capabilities, models, prompt, evals, the fixtures those evals need, and at most one new skill if nothing in the catalog covers the job. With a map and aspect given, the model may only require capabilities provided by that aspect's tools plus shared tools. Emit: the script writes the agent file, the fixtures, and any new skill; generated files are never overwritten, and a name clash aborts before writing. Validate: on failure the errors go back to the model for one repair pass [17]; if validation still fails, the generated files are removed. Evaluate: the runner executes the new agent's evals, and only on an all-pass is the agent name added to the aspect's agent list, editing only that line.

8.1Observations

Trait composition held under pressure. Three agents were given tasks that contradicted a trait or a domain rule (fix the injection, fix the clearance, remove the ground wire) and all three declined, explained in one sentence, and changed nothing. The read-only trait's text and its tool denial reinforced each other; the eval confirmed that the merged prompt produced the intended behavior rather than assuming it from the hierarchy.

Failures were in phrasing more often than in competence. Both failed runs of drc-checker detected every violation correctly; they failed because the fix was not stated as exactly one sentence naming one object. The remedy was in the skill, which now demands a PASS or FAIL line per file and a one-sentence fix. This is the kind of defect a judge with a precise pass condition catches and a casual read misses.

Negative evals matter. Every agent has at least one eval whose correct answer is "nothing is wrong" or "do nothing": a clean diff, a clean board, a schematic that already has its capacitors, a complete issue report. Agents that invent findings or make unneeded changes fail these, and a catalog without them would select for busy agents.

Cost is low enough to run evals on every change. The most expensive agent, which creates and verifies schematics with a top-tier model, costs 76 cents for four evals. The whole catalog runs for about two dollars.

9Discussion and threats to validity

Judge reliability. The judge is a language model and is cheaper than most agents under test; it can be wrong in both directions [15]. We mitigated this by writing pass conditions that name checkable facts and by giving the judge mechanical evidence (diffs, netlists, document dumps) rather than only the agent's message. Two agents' diffs were also inspected by hand. The judge and the agents are from the same model family, which may share blind spots.

Sample size. Six agents and 18 evals, plus two playbooks and four playbook evals, is an existence proof, not a statistical result. Each eval was run once in its final form; model nondeterminism means a repeat could fail. The run history of drc-checker (three runs to an all-pass) shows that evals are sensitive to skill wording.

Fixtures are small by design. A three-error board and a one-regulator schematic make pass conditions exact, but they do not show how agents behave on real designs. The result generalizes to the method, not to the agents' competence on production work.

Pack effects are measured on one pack and one subset. The re-gate attached a single vendored skill from one library. A pack that grants tools, changes reporting format, or runs to several thousand words would interact more strongly with agent traits, and the validator's rule 5 only checks what is declared, not what the text implies. The security-reviewer hedge shows that even a pure-text base can shift a judgment call; evals with a severity-sensitive pass condition are the only guard.

Self-authored evals. The meta-agent writes the rubric, the fixtures, and the pass conditions in one call. The issue-triager case shows these can disagree with each other, and that the disagreement is caught; it does not show that they cannot be jointly wrong. A human reviewed the rubric. The hand-written playbook eval that paired an issue with an unrelated diff (Section 8.3) shows the same for a human author, caught that time by an agent under test. Independent eval authorship would strengthen the gate.

Host-specific binding. Tool files contain absolute paths to a KiCAD installation, a Python virtual environment, and a design application. This is correct for the taxonomy, because the binding is meant to live in the tool file and the map, not in agents, but it means the catalog is not portable without editing those files.

A semantic decision made while building. In a trait, tools is additive and only denies restricts. Under that reading the hand-written agents are consistent. The alternative reading, that a trait's tool list is exhaustive, would have made runs-tests and read-only conflict on every tool but Bash. The rule is recorded in the catalog documentation so that it is not implicit in code.

10Open questions and future work

Playbooks beyond two. Both handoff forms have run (Section 8.3). Branching, retries, and a trigger that starts a playbook from an event are deliberately absent until an eval needs them; a handoff tests one field or one command, so a condition on two fields needs either a combined field or a second step; and a step sees only the previous step's diff, not the whole history of a long playbook.

On-demand pack skills. A pack's base is composed into every prompt, so it must stay small. Libraries such as superpowers keep most of their skills for on-demand loading through a skill-invocation tool. Giving the headless runner a per-workspace skills directory would let a pack declare an on_demand set beside its base, and would let evals test whether an agent invokes the right one.

Repeated runs and flakiness. Running each eval several times and reporting a pass rate would turn the gate from a single observation into a measurement, at a cost that Table 2 suggests is affordable.

Independent judges and eval authors. Grading with a model from a different family, and having evals authored separately from the agent they test, would address the two strongest threats in Section 9.

11Conclusion

An agent that assembles agents is reasonable with current models. The risk was never the ambition. It was building an elaborate type system around prompts, which behave like documents rather than classes. Replacing inheritance with ordered traits, skill ownership with declared requirements, per-agent tool attachment with capability contracts bound at the aspect, a base skill owned by a base agent with one vendored pack composed before every agent, and a missing evaluation step with a mandatory one gives the reuse the original design wanted without its fragility. The method is three words: compose, validate, evaluate. It now runs end to end, across code, design, firmware, and electronics, for under one US dollar per agent, and the one time the generator produced a flawed agent, the gate held. The same three words cover sequences of agents: a playbook is composed from routed agents, validated by rule 6, and evaluated on the path it takes as well as on what it produces.
